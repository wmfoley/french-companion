# ADR-0005 — Android native household PIN derivation

**Status:** FC-004N.2B implementation approved by owner, 2026-11-11. Updated Kotlin APK build/upload and physical household acceptance remain separately gated.

## Evidence and scope

Owner verified FC-004N.2A on Android 12: both public vectors passed four consecutive runs each. Initial native durations 3,637.5 / 3,717.3 ms; round trips 3,643.3 / 3,723.8 ms; six further runs were comparable. These are owner-reported proof results, not agent-measured household setup/verification performance. They justify replacing Android's slow Noble JS derivation, without changing the work factor.

## Decision

Extend `FcNativePbkdf2` with fixed-parameter `derivePin(pin, saltHex)` and a synchronous API-26+ availability probe. Use the same platform `PBKDF2WithHmacSHA256` helper as the retained development proof, called inside `withContext(Dispatchers.Default)`. A process-wide native guard covers proof and auth; a JS engine guard prevents overlapping derivations until settlement. Generic coded native errors omit causes/provider details; JS forwards fixed messages, never raw exceptions or output in diagnostics.

Preserve exactly PBKDF2-HMAC-SHA256, 600,000 iterations, six ASCII digits including leading zeros, 16-byte random salt from Expo Crypto, 32-byte verifier, and the existing lowercase hex credential record. The native helper has no configurable work factor. It returns hex only to the internal credential adapter, never a UI/log. Clear mutable native buffers best-effort; immutable JS/JVM strings cannot be promised immediate erasure.

Native composition uses optional loading and rejects missing methods, old proof-only APKs, unsupported API or malformed output. No Android Noble/WebCrypto fallback. Availability is checked before household storage/setup/unlock and on protected commands; absent support locks access without changing stored data. Expo Go remains launchable for standalone learning/proof-unavailable screens. Web retains its `.web.js` IndexedDB/WebCrypto composition and existing grading/learning behaviour; no crypto/storage dependency or config change.

SQLite/SecureStore binding, credential identifiers, pending/ready recovery, revision checks, cooldown and parent session/lifecycle semantics remain those of ADR-0003 and FC-004N.1. Cancelled derivation may finish but cannot initialize afterward; already-started strict binding can finish without unlock. No migration, reset, automatic PIN replacement or persistent unlock token. Existing compatible credentials need no rehash or rewrite just to use the native engine.

## Build and acceptance gate

ADR-0004's proof-only restriction is superseded only for this approved integration. Both proof and auth now share a fixed helper. This Kotlin change requires a new APK; the old proof APK deliberately fails household authentication after a Metro JS update. Do not cloud-build/upload without separate approval. Retain `com.frenchcompanion.dev` and the existing signing identity; update in place rather than uninstalling or clearing data. Expo Go data remains separate and untouched.

Node tests exercise the adapter against an independently implemented Node stand-in; they do not execute Android. Retained native proof must pass again on the rebuilt APK, followed by [household acceptance](../development/ANDROID_HOUSEHOLD_ACCEPTANCE_FC004N_2B.md). Automated/export checks do not establish native Kotlin compilation or physical correctness.
