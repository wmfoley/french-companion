# ADR-0003 — FC-004N native household foundation

**Status:** Approved by owner on 2026-11-10; implementation subject to physical Android acceptance.

## Scope and compatibility

Complete FC-004 on Android/Expo Go without changing assignment schema version 1, exercise types, learning interactions or approval semantics. This supersedes ADR-0002's native-disabled boundary and absolute five-minute session lifetime. Use true five-minute **inactivity** expiry consistently on web and native. FC-005 review/correction/Approve All, FC-003A randomization, mixed sprints, camera, OCR, AI and curriculum enrichment remain out of scope.

Approved exact dependencies: Expo SQLite 58.0.15, SecureStore 58.0.2, Crypto 58.0.7, and @noble/hashes 2.4.0. Official SDK-58 references list all three Expo modules as included in Expo Go. Noble is JavaScript; no custom native module/build is required for PBKDF2. Do not enable SQLCipher, biometric requirements or unapproved native configuration: SQLCipher is not available in Expo Go. Config plugins added by Expo installation apply to future standalone builds, not changes to the Expo Go binary.

Sources: [SQLite](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/), [SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [Crypto](https://docs.expo.dev/versions/v58.0.0/sdk/crypto/), [Noble PBKDF2](https://github.com/paulmillr/noble-hashes#pbkdf2). Physical device compatibility and latency remain separate acceptance checks.

## Persistence

Native `localHousehold.js` composes the existing shared service with `sqliteStore.js` and native credentials. `.web.js` retains IndexedDB/Web Crypto. SQLite stores one native-versioned installation record in `french-companion-local-v1.db`; the record wraps the existing household/documents and a credential identifier. Assignment policy, revision counters, source fidelity and approval evidence keep their existing meanings. No generalized repository/roles/ORM.

The native facade returns the same in-memory shape expected by `householdService`, but removes the credential record before writing SQLite. A project-namespaced SecureStore entry contains the binding identifier plus salt, derivation parameters and verifier. Reads hydrate credentials from SecureStore; missing, unreadable, corrupt or mismatched credentials block all household operations with a clear explanation. Neither database nor PIN resets automatically. SQLite lesson/policy data is not encrypted by this app; Android SecureStore protects credential material at rest, not arbitrary modified app code.

Each adapter instance queues operations and uses `withExclusiveTransactionAsync`; the callback reads current state, runs the shared synchronous mutation/authorization checks and writes a parameterized JSON payload. Exceptions roll back; results return only after commit. Other connections may receive a database-lock failure rather than a successful stale save. Revision comparisons and strict policy fallback remain in the shared service. No permissive memory fallback.

## Minimal two-store initialization

SQLite and SecureStore cannot share a transaction. Only initial setup writes both:

1. Commit a `pending` row containing the credential ID and initial strict, empty household state, without the verifier.
2. Write the matching credential record to an empty SecureStore slot; never overwrite an existing secret.
3. Verify the binding and finalize the row as `ready` in another SQLite transaction.

A restart after step 2 may finalize only that same matching initial strict/empty setup. This grants no parent unlock and never restores an independent policy. A pending row without matching readable credentials remains locked; incomplete setup is not treated as a new installation. An orphan secret without a row also remains locked. There is no destructive recovery/reset feature in this ticket; unmatched interruptions require separately authorized recovery. Do not clear Expo Go's host data as an automated repair.

Ordinary policy, cooldown and assignment writes update SQLite only. PIN changes are rejected by the adapter. Source material is never rewritten by persistence or practice.

## PIN and session handling

**Superseded native KDF selection:** FC-004N.2B/[ADR-0005](ADR-0005.md) replaces the native Noble implementation described below with Android provider derivation; parameters, serialization, storage and lifecycle semantics remain unchanged. No Android JS fallback. Web continues WebCrypto.

Shared credential formatting/validation/comparison supports injected platform primitives. Web uses Web Crypto; native uses Expo Crypto secure random salts and Noble's asynchronous PBKDF2-SHA256. Keep 600,000 iterations, 16-byte salt and 32-byte verifier unchanged. PIN input is six ASCII digits; no plaintext PIN persistence/logging. Async derivation yields between work chunks; performance on Hermes/tablet must be measured, not inferred from desktop Node.

Service-level concurrent unlock attempts are rejected, independently of UI busy controls. Busy state is also synchronously guarded in the Parent Area. In development, successful unlock shows total elapsed time (derivation plus local storage) for repeatable tablet measurements. No production benchmark telemetry.

Opaque parent capabilities expire after five idle minutes. Only explicit authenticated user input via `noteParentActivity` refreshes the deadline. Status polling, re-renders, asynchronous saves and background tasks do not. Application composition uses a monotonic clock. Expired capabilities cannot refresh themselves. Leaving Parent Area/background/inactive AppState immediately locks and cancels pending unlock authorization; sessions never persist. Normal practice rechecks on resume and before transitions, with the existing two-second poll.

## Verification limits

### FC-004N.1 approved lifecycle clarification

The first physical setup test stalled for minutes while navigation remained responsive; root cause is unconfirmed and Android acceptance is blocked. Development-only stage instrumentation, capped at 48 emissions per operation / 32 retained events and three slow warnings, measures derivation and persistence without credentials or raw exceptions. An on-device Parent Area panel and safe console events support capture without Android Studio. No KDF/scheduler optimization or recovery reset is authorized in this ticket.

Setup concurrency is guarded in the shared service until actual settlement, independently of screen busy state. Focus/operation identities prevent late tasks/status/poll failures from updating a new visit. Leaving/backgrounding clears visible busy/input state but does not pretend to stop underlying computation/native requests. Cancellation is checked immediately before the first native household INSERT, after any async ID generation; once issued, complete the existing strict binding protocol where possible. Completion after leaving never unlocks parent access. Slow warnings never release guards. See [diagnostic procedure](../development/ANDROID_PIN_DIAGNOSTICS_FC004N_1.md).

Node tests use real SQLite SQL through a small Expo-shaped test connection and a simulated SecureStore. They test transaction/init/credential failure paths but do not execute Android Keystore or Expo native bridge code. PBKDF2 equivalence tests execute the actual native JavaScript engine against Web Crypto. Web browser regressions use real IndexedDB. Android export proves bundle compatibility only; physical Expo Go acceptance, background behavior, process interruption and PIN latency remain manual checks.
